# Writing prose

The mechanical rules every markdown file is held to, and the voice and audience each file is judged
in, are in `docs/standards/writing_standard_v1.0.md` and `writing-profile.yaml`. What follows is the
judgement no gate makes: the document reviewer reads a document against it, and the editor rewrites
what it finds ([[reference_writing_standard_design]]).

- Write in the voice the profile gives the file, to the traits of its file in
  `docs/standards/voices/`. A file no rule names takes the default voice.
- Lead with the point. A sentence that announces what comes next, or recaps what came before, goes.
- Cut filler: a word whose removal changes nothing.
- State a claim once and plainly. Hedge only where the evidence is partial and say what is unknown;
  never stack one qualifier on another.
- Never flatter the reader, the work or a tool.
- List as many items as there are, not three because three sounds finished.
- Vary the rhythm. A run of sentences of one length and shape reads as generated.
- Replace a vague claim (robust, powerful, significant, comprehensive) with the number, the name or
  the behavior that shows it.
- A colon in a heading earns its place as a label, as `Step 1: Install` and `Decision <ID>:` do; a
  title restated after a colon does not.
- Once a term or convention is locked, keep it in every document. Consistency outranks cleverness.
- Spell vendor and product names exactly as the vendor does, and use the project's locked terms,
  from section 10 of `docs/standards/document_production_standard_v1.0.md`.
- In a production document, explain the project's own terms or leave them out: the gate catches
  development references, not jargon.
